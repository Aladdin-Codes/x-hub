# Common Pitfalls

> **When to read this:** Scan before coding and check each item before delivery. Every item is based on a real-world issue.

1. **Naming:** Use “extension,” not “plugin.” The `id` must use **your own** reverse-domain name (`com.your-domain.<short-name>`). **`com.x-hub.*` is a platform-reserved namespace** for official first-party extensions; third-party submissions are rejected by the server, while local preflight only warns, so the problem may not surface until upload.
2. **`entry` must be HTML**, not a `.js` file.
3. **Use `deploy` for an npm script**, not `install` (npm lifecycle hooks may trigger unexpectedly).
4. **Service port:** Read `process.env.PORT` and listen only on `127.0.0.1`; `/healthz` is the health-check path.
5. **Frontend-to-backend calls:** Use `window.xhub.service.request`; don't fetch the port directly.
6. **Check the bridge API status** with `runtime.info().capabilities`. Implemented: `runtime(info/open/callExtension/openPermissions)`, `storage.*`, `config.*`, `sharedStorage.*`, all `data.*` reads and writes, `fs.saveText/saveFile/saveAs`, `service.request`, `theme.get`, `events.on/emit`, `openExternal`, `ui.notify`, `clipboard.readText/writeText`, and `expose`. Not implemented: `net.*`, `system.*`, `ui.toast`, `fs.readText/writeText/readDir/exists`.
6b. **Always use `window.xhub.openExternal(url)` for external links**: x-hub hosts extension iframes in Tauri/wry. If the host has not registered a new-window handler, wry rejects WebView2's `NewWindowRequested` with `SetHandled(true)`, so `target="_blank"` and `window.open()` **silently fail in the host** (nothing happens). Worse, they “seem to work” in a standalone browser preview, so this issue only appears inside the host. Only `http(s)://` URLs are allowed.
    - **The user, not the extension, chooses where links open**: In the extension details dialog, users can set the “Link opening behavior” for each extension. The default is the **in-app browser window**; they can also choose “Browser” (the system default browser). Extension code should only call `openExternal`, which supports both modes; don't implement your own browser choice.
    - **The host automatically handles ordinary `<a href="http(s)://…">` links** (the bridge intercepts the click in the capture phase and calls `openExternal`), so just add the link; no click handler is needed. Conversely, **don't attach custom click logic** (confirmation dialogs, analytics, etc.) to an external `http(s)` `<a>`—the host takeover swallows those handlers (`stopPropagation`). For custom click behavior, use a button + `openExternal`, not `<a href=http…>`.
6c. **For multiple module variants, apply the query variant to the DOM attribute yourself.** The host sets `data-xhub-variant` and broadcasts an event, but `?xhub-variant=dual` is available only on the initial frame. For CSS-only branches (`:root[data-xhub-variant="dual"]`) to work, after reading the query call `document.documentElement.setAttribute('data-xhub-variant', v)`; otherwise variant-specific CSS never activates in browser previews.
7. **Declare permissions**: reading host data requires `data:read`, writing data requires `data:write`, saving files to the download directory requires `fs`, broadcasting events requires `events`, cross-extension shared storage requires `shared-storage`, and external links via `openExternal` require `open-url`. Calling an API without its permission is rejected (`PERMISSION_DENIED`). For `openExternal`, the host displays a warning, but the link still **won't open**—don't wait for a user report to discover the missing permission. A service extension's `service.request` may also be rejected at runtime with `PERMISSION_DENIED` after the user revokes authorization; provide a “Go to permissions” button that calls `xhub.openPermissions()` (see `service.md`).
8. **Use `var(--xhub-page-bg, transparent)` for the page background** (no wallpaper = host page background; wallpaper = transparent); use `var(--xhub-surface)` for content surfaces. **Never use `--xhub-bg-page` as the page background** (it covers the wallpaper, and transparent mode produces white text on white). For more wallpaper-specific styling, use `data-xhub-wallpaper` / `data-xhub-wallpaper-clear` / `data-xhub-immersive`.
9. **Before deploying a service extension**: If x-hub is running and has the extension's backend files locked, `deploy` fails with EPERM. Quit x-hub before deploying.
10. **Field names are case-sensitive**: `openIn`, `minSize`, `dependsOn`, and `backend.engine.minVersion` use camelCase; incorrect casing causes parse failures.
11. **Use `namespace.method` for `requires`**: This is a host bridge API capability name (for example, `data.notes.list`), not a permission name (`data:read`). An incorrect value makes the extension center show “Missing capability.”
12. **Don't use CDNs**: Tailwind, Font Awesome, and externally hosted fonts may be blocked by CSP or offline conditions in the host webview. Keep entry-point resources local.
13. **Provide fallback declarations for both themes**: Use light fallbacks in `:root` and dark fallbacks in `:root[data-xhub-theme="dark"]`; otherwise standalone previews without the host will look wrong in dark mode. Derived accent tokens (primary / soft / text) are easiest to miss.
14. **`xhub.storage` is asynchronous and shared across surfaces**: Read saved values before the first render. A given extension's `module` / `view` / `window` / `drawer` share the same storage; make key names unique (for example, `'progress'`, `'notes'`).
15. **`window` / `drawer` share an entry with `view`**: Point `entry.window` directly to `./view/index.html`; don't duplicate the page.
16. **`--xhub-bg-page` is a gradient, not a color**: `color: var(--xhub-bg-page)` is invalid and silently falls back to the inherited color (it may “look right by accident” until the theme changes). Explicitly choose text colors on solid accent backgrounds (light theme accent is dark → white text; dark theme accent is light → dark text).
17. **`data.*` `update` calls replace the entire object**: Omitted optional fields may be written as empty values (`notes.update` without `content` clears the body). Read with `get`, merge, then submit. Use the `expectedVersion` optimistic lock for concurrent `todos` / `stickies` writes; conflicts reject with `VERSION_CONFLICT`.
18. **CSS has no conditional expressions**: Use attribute selectors such as `:root[data-xhub-variant="compact"] { … }` for module variant branches; CSS cannot evaluate `var(--xhub-variant) === 'compact' ? … : …`.
19. **Don't infer the host data root from `__dirname`, and don't write data directly to the extension directory**: In a mounted development directory, the extension's parent is a version directory or arbitrary source directory, **not** `extensions`, so inference fails. Falling back to the extension directory writes `data.json` / `sync.log` into the source tree. If that is your **release source directory**, user data is packaged and uploaded with the extension (a real incident put shared todo data in a review package). Write persistent data inside the extension's **`.data/`** directory instead (dot-prefixed directories are skipped by host packaging and hot reload). Put backups from old-data migrations there too. The host's own `.storage.json` / `.config.json` files are also inside the extension directory (which is your source directory in mounted mode); those are host-managed key/value stores, not your data directory.
20. **If the backend won't start, check the logs instead of guessing**: The host writes service backend stdout/stderr to `<data-root>\logs\service\<extension-id>.log` (max 1 MB per file, with a `----- service started <time> -----` separator on each launch). If health checks fail, `x-hub.log` also includes **`exit=<code>` + the last 20 log lines**. `runtime.info().serviceReady === false` only means the port wasn't reachable; the backend may not have started, may have crashed, or the port may be occupied. Open that log first. Don't tell users “Node is downloading” or make other guesses.
21. **Normalize paths before passing them to external programs (Windows `\\?\` prefix)**: Since v0.6.2, the host normalizes the script path passed to the backend (removing the prefix), but `__dirname` itself may still be a verbatim path when mounted (`\\?\C:\…`). Before the backend spawns a child process, calls tools such as `ffmpeg` / `git`, or inserts a path into command-line arguments, strip the prefix (`\\?\C:\x` → `C:\x`, `\\?\UNC\srv\share` → `\\srv\share`); otherwise the external program may not recognize the path (even Node itself cannot load a script path with the prefix).
22. **A `module` card viewport can be as short as ~86px; don't assume “at least 150px”**: Card height comes from the workbench grid (minimum row height 36px). A 4×2 small cell may have only about 86px of content height, **minus about 30px more if the host header is enabled** (a host bug in 0.6.3 and earlier once left the iframe at the browser default of 150px, clipping short cards; that was fixed). Use `height: 100%` + `box-sizing: border-box` + `cqh` / `clamp()` for layout, and let `overflow: hidden/auto` handle overflow. A fixed `min-height` or reliance on the default 150px height will clip in short cells. The host **does not add** iframe padding; add your own (12px recommended; see `surfaces.md`).
23. **The host header is off by default; don't duplicate its title**: Extension `module` cards **have no host header by default**; draw the card content yourself. Only with `"moduleOptions": { "defaultHideTitle": false }` does the host render a “brand-color icon + `manifest.name`” header at the top. In that case, **don't draw the same title again** and confirm the card name. Users can override the author default per card with “Aa” in the layout editor.
24. **Manifest icons must include their own colors; avoid `currentColor` and transparent icons that are pure black or white**: Host icons are rendered with `<img>` (pinned sidebar, extension center, market cards). SVGs loaded through `<img>` do not inherit color, so `stroke="currentColor"` falls back to **black** per SVG behavior. Icons generated with the common “minimal icon = currentColor stroke” pattern will be black and unreadable in dark themes and over wallpaper (the sidebar is transparent and icons sit directly on photos). Use app-icon-like colors: preferably a rounded brand-color tile with a white/light glyph, or a medium-to-high-luminance glyph. Check against both light and dark backgrounds before delivery. The same applies to PNG icons; don't ship a pure-black logo on a transparent background.
